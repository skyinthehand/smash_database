# Feature Specification: 未開催トーナメントの管理

**Feature Branch**: `010-upcoming-tournaments`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "未開催(scheduled/upcoming)のstart.ggトーナメントを一部リポジトリで管理する機能。対象は当面JPのみだが将来他地域にも拡張できる構造にしておく。参加人数(num_entrants)も保存したい。フォルダは作らず1本のJSONL索引ファイルのみで管理する。未開催の間はデータが変わってよい前提で、毎日全件を取得し直して完全上書きする。毎日のGitHub Actionsワークフローに組み込む。追加でscheduledEventsについても既存のラベル判定機構によるラベル判定だけは行っておきたい。"

## Clarifications

### Session 2026-09-10

- Q: 参加人数を大会一覧の取得と同時にまとめて取れない(1回のクエリに
  含められない)ことが判明した場合、どう扱うか？ → A: 既存の履歴収集と
  同じ「トーナメントごとに種目一覧→種目ごとに詳細」の個別呼び出しに
  フォールバックし、コストが増えても必ず参加人数を取得する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 開催前の大会一覧を把握する (Priority: P1)

保守担当者として、まだ開催されていない(start.gg上で開始日時が未来の)JPの
対象大会の一覧を、既存の(開催済み大会の)履歴データとは別に、リポジトリ内で
参照できるようにしたい。

**Why this priority**: これが無いと機能自体が成立しない、本フィーチャーの核心。

**Independent Test**: JP国コードを対象に取得処理を実行し、開催前の大会が
索引ファイルに1件ずつ記録されること、既に終了した大会は含まれないことを
確認できる。

**Acceptance Scenarios**:

1. **Given** start.gg上に開催前(開始日時が未来)のJP対象大会が存在する、
   **When** 取得処理を実行する、**Then** その大会が未開催大会の索引ファイルに
   記録される。
2. **Given** start.gg上に既に開始済み・終了済みの大会が存在する、
   **When** 取得処理を実行する、**Then** その大会は未開催大会の索引ファイルに
   含まれない。

---

### User Story 2 - 参加人数を確認する (Priority: P2)

保守担当者として、開催前の各種目における現時点での参加登録人数を確認し、
締切前の集まり具合を把握したい。

**Why this priority**: 主要な付加価値だが、一覧そのもの(P1)が無いと意味を
持たないため、その次の優先度とする。

**Independent Test**: 取得結果の各種目レコードに参加人数が含まれ、
start.gg上の実際の登録人数と一致することを確認できる。

**Acceptance Scenarios**:

1. **Given** 開催前の種目にX人の参加登録がある、**When** 取得処理を実行する、
   **Then** その種目レコードの参加人数がXになる。

---

### User Story 3 - 開催前の種目にもラベルを付与する (Priority: P3)

保守担当者として、開催前の種目についても、大会名・種目名から機械的に判定
できるラベル(既存のイベントラベリング機構と同じ判定ルール)を確認したい。

**Why this priority**: 既存のラベリング機構(汎用イベントラベリング機構)の
再利用であり、P1・P2が実現していれば追加コストは小さい付随機能のため。

**Independent Test**: 既存のラベル判定ルールに合致する名前を持つ開催前の
種目について、そのレコードに該当ラベルが記録されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 種目名が既存の特定のラベル判定ルールに合致する、
   **When** 取得処理を実行する、**Then** その種目レコードに該当ラベルが
   含まれる。
2. **Given** ラベル判定ルールが要求するデータ要件を満たさない、
   **When** 取得処理を実行する、**Then** ラベル判定は行われず、その旨が
   判別できる状態のまま記録される(既存のラベリング機構と同じ挙動)。

---

### Edge Cases

- 開催期間中(開始日時は過去だが終了日時が未来、つまり進行中)の大会は
  対象外とする(まだ「開催前」ではないため。終了後は既存の履歴収集が拾う)。
- 前日まで一覧に載っていた大会が、開催日を過ぎて一覧から消える(以後は
  既存の履歴収集側の管轄に移る)。両者間のデータの引き継ぎは本フィーチャーの
  スコープ外とする。
- start.gg側で大会の日程が延期された場合、次回の全件再取得で自然に最新の
  日時に更新される(差分検出は不要)。
- start.gg側で大会自体が削除・非公開化された場合、次回の全件再取得で
  自然に一覧から消える。
- 本フィーチャーの取得処理自体が失敗しても、既存の(開催済み大会の)日次
  データ更新は影響を受けず継続される。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、指定した国コード(既定はJP。将来的に他の地域にも
  適用できる形)について、start.gg上でまだ開始されていない対象ゲームの
  公開済み大会の一覧を取得しなければならない。
- **FR-002**: システムは、取得した各大会について、大会ID・名前・開催予定
  日時(開始・終了)・会場情報・大会ページURLを記録しなければならない。
- **FR-003**: システムは、各大会に属する各種目について、種目ID・種目名・
  現時点の参加登録人数・オンライン開催かどうか・種目の状態を記録しなければ
  ならない。参加登録人数を大会一覧の取得と同時にまとめて取得できない場合、
  既存の履歴収集と同じ「トーナメントごとに種目一覧を取得→種目ごとに詳細を
  取得」という個別呼び出しにフォールバックし、コストが増えても必ず参加
  登録人数を取得しなければならない(FR-003a)。
- **FR-004**: システムは、各種目について、既存のイベントラベリング機構
  (大会名・種目名に基づくルールベース判定)を用いて算出したラベルおよび
  ラベル判定バージョンを記録しなければならない。
- **FR-005**: システムは、この未開催大会のデータを、既存の(開催済み大会の)
  履歴データとは別の、単一の索引ファイルとして保存しなければならない
  (大会・種目ごとの個別ディレクトリは作成しない)。
- **FR-006**: システムは、取得処理を実行するたびに、この索引ファイルの
  内容を完全に洗い替え(既存内容を破棄し、最新の取得結果で置き換え)
  なければならない。
- **FR-007**: システムは、既存の(開催済み大会の)履歴データを本フィーチャーの
  処理によって一切変更してはならない。
- **FR-008**: システムは、この取得処理を、既存の日次自動更新の一部として
  実行しなければならない。
- **FR-009**: この取得処理が失敗した場合であっても、既存の(開催済み大会の)
  日次データ取得・保存処理は継続されなければならない。

### Key Entities *(include if feature involves data)*

- **未開催大会**: start.gg上でまだ開始されていない大会。大会ID・名前・
  開催予定日時・会場情報・URLを持つ。
- **未開催種目**: 未開催大会に属する個々の種目。種目ID・名前・参加登録
  人数・状態・ラベルを持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: JPの未開催大会一覧が、日次の自動更新後、常に24時間以内に
  取得された情報として参照可能である。
- **SC-002**: 一覧に含まれる各種目の参加登録人数が、取得時点のstart.gg上の
  値と一致する。
- **SC-003**: 開催日を過ぎた大会は、翌日の更新後には一覧から消えている。
- **SC-004**: 本フィーチャーの取得処理が失敗しても、既存の(開催済み大会の)
  日次データ更新は影響を受けず正常に完了する。

## Assumptions

- 対象ゲームは既存の履歴収集と同じ種目(スマッシュブラザーズSP)とする。
- 会場の座標・住所等はstart.ggが返す値をそのまま保存し、追加の加工
  (ジオコーディング等)は行わない。
- 「開催中」(開始日時は過去だが終了日時が未来)の大会は本フィーチャーの
  対象外とする(既存の履歴収集が終了後に拾う)。
- 未開催大会の一覧取得・地域絞り込みが、start.gg側の提供機能の範囲内で
  実現可能であることは、実装時に実際のAPI疎通で確認する前提とする
  (現時点では未検証)。参加登録人数について、一覧取得への統合が
  できなかった場合の扱いはFR-003aで規定済みのため、この点は
  ブロッカーにならない。
- 既存のイベントラベリング機構(ルール定義・判定ロジック)は変更せず、
  そのまま呼び出して再利用する。
