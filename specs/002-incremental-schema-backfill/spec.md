# Feature Specification: 既存イベントへのスキーマ追加フィールドの段階的バックフィル

**Feature Branch**: `002-incremental-schema-backfill`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "phaseOrderの追加やイベント参加したゲストアカウントの数集計など追加実装を行った際に、すでに取得済みのイベントも含めてイベントデータを補う仕組みを作りたい。APIアクセスが多くて一連のタスクにできない場合は、スケジュール処理で、例えば１時間毎とか一日ごととかに動くような処理にしてもよい。"

## User Scenarios & Testing *(mandatory)*

`matches.json` への `phase_order` 追加や、`attr.json` への `guest_entrant_count`
(start.gg アカウント未リンクの参加者数)追加のように、今後もスキーマにフィールドを
追加する変更は継続的に発生する見込みである。

現状の方針(本会話で確認済み)は「新規に追加したフィールドは、新規取得・再取得された
イベントにのみ付与され、既存の約26,736件のイベントディレクトリには遡って付与しない」
というものである。この結果、スキーマにフィールドを追加するたびに、新旧フィールドを
持つデータが恒久的に混在し続け、`docs/data_model.md` 上のスキーマと実データの乖離が
広がっていく。

既存の手動ツールとして `scripts/fix/backfill_events.py`(要 `--event_ids_file` 等)や
`data_force_refresh_backfill.yml`(`workflow_dispatch` で日付範囲を指定して全項目を
再取得)は存在するが、いずれも人手による都度実行が前提で、対象期間の全イベントを
まるごと再取得するため、「新しく追加された特定フィールドだけを埋めたい」という
目的に対しては API 呼び出しが過大になる。全26,736件を一度に処理しようとすると、
start.gg のレート制限や1回のワークフロー実行時間の制約に収まらない可能性が高い。

### User Story 1 - スケジュール処理で段階的にバックフィルする (Priority: P1)

メンテナとして、新しいスキーマフィールド(`phase_order`, `guest_entrant_count` など)が
追加された際に、既存の全イベントを一度に再取得するのではなく、日次または時間単位の
スケジュール実行によって少しずつ対象イベントを処理し、最終的にすべての既存イベントに
新フィールドが行き渡るようにしたい。

**Why this priority**: これが実現しないと、スキーマ追加のたびに「新旧混在データ」が
恒久的に残り続け、今回の `001-consolidate-validation-checks` で導入する
`guest_entrant_count` ベースの閾値調整のような機能も、再取得されない大多数の
既存イベントには一切効果が及ばないままになる。

**Independent Test**: `phase_order` を持たない `matches.json` を含む一時イベント
ディレクトリ群を用意し、バックフィル処理を1回(1バッチ分)実行して、一部のイベントに
`phase_order` が付与され、進捗カーソルが更新されることを確認する。同じコマンドを
再実行すると、前回処理した分はスキップされ、続きから処理されることを確認する。

**Acceptance Scenarios**:

1. **Given** 新フィールドを持たない既存イベントが多数存在する、**When** バックフィル処理が
   1回実行される、**Then** 設定された上限件数までのイベントが処理され、新フィールドが
   付与される。
2. **Given** 前回の実行で一部のイベントまで処理済み、**When** バックフィル処理が再度
   実行される、**Then** 前回の続きから処理を再開する(重複処理・処理漏れをしない)。
3. **Given** 全既存イベントの処理が完了している、**When** バックフィル処理が実行される、
   **Then** 処理対象がないことを検知し、何もせず正常終了する。

---

### User Story 2 - 将来追加されるフィールドにも同じ仕組みを再利用する (Priority: P2)

メンテナとして、今後新しいフィールドをスキーマに追加するたびに、専用のバックフィル
スクリプト・ワークフローを1から作り直すのではなく、同じ仕組みに「このフィールドが
欠けているイベントを対象にする」という条件を追加するだけで対応したい。

**Why this priority**: `phase_order` と `guest_entrant_count` は今回の直接のきっかけに
過ぎず、スキーマ追加は今後も繰り返し発生する。仕組みを使い捨てにすると、同じ設計上の
問題(新旧データの恒久的な混在)が毎回再発する。

**Independent Test**: 「対象判定条件」に新しいフィールド名を1つ追加する変更だけで、
その新フィールドを欠くイベントがバックフィル対象として検出されることを確認する。

**Acceptance Scenarios**:

1. **Given** バックフィル対象の判定条件に新しいフィールドが追加された、**When** バックフィル
   処理が実行される、**Then** そのフィールドを欠く既存イベントも対象として処理される。

---

### User Story 3 - 既存の取得基盤・運用ルールと衝突しない (Priority: P2)

メンテナとして、このバックフィル処理が、既存の日次更新ワークフローや他のバックフィル
ワークフローと衝突（同時実行によるブランチ競合やAPIレート制限の奪い合い）しないように
したい。

**Why this priority**: 本リポジトリでは自動化はすべて `chore-update` ブランチへの
コミットを経由し、`main` への反映はPRレビューを通す運用が徹底されている
(`update_tournament.yml` / `update_user.yml` と同じ concurrency グループを使用)。
この規律を崩すと、ブランチの巻き戻り・コンフリクトが発生する。

**Independent Test**: 本機能のワークフローが `chore-update` ブランチ以外にコミットしない
こと、および既存のリトライ・バックオフ機構(`fetch_data_with_retries` / `fetch_all_nodes`)
を経由してAPIを呼んでいることをコードレビューで確認する。

**Acceptance Scenarios**:

1. **Given** 日次更新ワークフローと本機能のワークフローが同時にトリガーされうる、
   **When** 両方が実行される、**Then** 同一の concurrency グループにより一方が待機/
   キャンセルされ、`chore-update` ブランチへの競合コミットが発生しない。

---

### Edge Cases

- スケジュール実行中に start.gg API のレート制限(429)やクエリ複雑度エラーに遭遇した場合
  → 既存のリトライ・バックオフ・ページサイズフォールバック機構をそのまま再利用し、
  本機能独自のリトライ処理を実装しない。
- 1回の実行で処理しきれなかった大規模イベント(参加者数が非常に多い等)の途中で
  ワークフローのタイムアウトに達した場合 → 次回実行時にカーソルから再開できる粒度
  (イベント単位)で進捗を保存する。
- バックフィル対象の判定条件に含まれるフィールドが、今回のみ一時的に追加される
  (将来的に条件から削除される)場合 → 対象判定はイベントディレクトリのスキャン時に
  都度評価するため、条件を減らせば自動的に対象範囲も狭まる。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、既存のイベントディレクトリのうち、指定されたスキーマフィールド
  (例: `attr.json` の `guest_entrant_count`、`matches.json` の各要素の `phase_order`)が
  欠けているものを検出しなければならない。
- **FR-002**: システムは、1回の実行で処理するイベント数の上限を設定可能にしなければ
  ならない(`scripts/fetch/refresh_users.py` の `--max_users` と同様のパターン)。
- **FR-003**: システムは、実行間で進捗(どこまで処理したか)を永続化し、次回実行時に
  前回の続きから処理を再開しなければならない(`scripts/fetch/refresh_users.py` の
  `--cursor_path` と同様のパターン)。カーソルはイベント単位の粒度で保存する。
- **FR-004**: システムは、GitHub Actions のスケジュール実行(`schedule` トリガー、
  例: 1時間毎または1日1回)によって、手動操作なしに定期的に実行されなければならない。
  手動実行(`workflow_dispatch`)も可能にする。
- **FR-005**: システムは、対象フィールドが既に存在するイベントには API アクセスを
  行わず、欠けているイベントのみを再取得対象にしなければならない。
- **FR-006**: システムは、対象イベントの再取得において、`scripts/utils.py` の
  `fetch_data_with_retries()` / `fetch_all_nodes()` 等、既存のリトライ・バックオフ・
  ページネーション機構のみを使用し、独自のAPIアクセス実装を追加してはならない
  (Constitution V 準拠)。
- **FR-007**: システムは、データ変更を `chore-update` ブランチへコミットし、`main` への
  反映は既存の PR フローを経由しなければならない。`main` へ直接 push してはならない
  (Constitution IV 準拠)。
- **FR-008**: システムは、既存の日次更新ワークフロー(`update_tournament.yml` /
  `update_user.yml`)と同一の concurrency グループ(`chore-update-branch`)を使用し、
  `chore-update` ブランチへの同時書き込み競合を防がなければならない。
- **FR-009**: バックフィル対象フィールドの判定条件は、コード変更のみで追加・削除
  できる形で管理され、フィールドごとに専用のスクリプト・ワークフローを新規作成する
  ことを必須としてはならない。
- **FR-010**: 全既存イベントの処理が完了している(欠けているフィールドを持つイベントが
  存在しない)場合、システムは何もせず正常終了しなければならない。

### Key Entities *(include if feature involves data)*

- **Backfill Target Field**: バックフィル対象として登録されたスキーマフィールド
  (対象ファイル種別、フィールド名、欠落判定条件を持つ)。
- **Backfill Cursor**: 直近に処理したイベント(または処理位置)を示す永続化された
  進捗マーカー。次回実行の開始位置を決定する。
- **Event Directory**: `attr.json` / `matches.json` / `seeds.json` / `standings.json` を
  含む1イベント分のデータ一式(`001-consolidate-validation-checks` と共通のエンティティ)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: スキーマに新フィールドを追加した後、人手による一括再取得を行わなくても、
  スケジュール実行の繰り返しにより、既存の約26,736件のイベントすべてに最終的に
  新フィールドが行き渡る。
- **SC-002**: 各回のスケジュール実行は、既存ワークフローのタイムアウト予算内
  (`update_tournament.yml`: 120分、`update_user.yml`: 360分 が参考値)に収まる。
- **SC-003**: 新しいフィールドをバックフィル対象に追加する作業が、新規スクリプト・
  新規ワークフローの作成を伴わない、小さな設定変更で完了する。
- **SC-004**: バックフィル処理と既存の日次更新ワークフローが同時にトリガーされても、
  `chore-update` ブランチの競合や壊れたコミット履歴が発生しない。

## Assumptions

- 本機能が最初に対象とするフィールドは `phase_order`(`matches.json`)と
  `guest_entrant_count`(`attr.json`、`001-consolidate-validation-checks` で定義)だが、
  本 spec が定義するのはこれらに限定されない汎用的なバックフィル機構である。
  各フィールド固有のビジネスロジック(`guest_entrant_count` の算出方法など)は
  それぞれの機能の spec(`001-consolidate-validation-checks` 等)側の責務とする。
- `guest_entrant_count` や `phase_order` の取得には、既存の `download_all_set()` /
  `download_standings()` 等、既存の全量再取得系の関数を流用する想定であり、
  「特定フィールドだけを軽量に取得する」差分取得の最適化は本機能のスコープに
  含めない(将来の改善余地として残す)。
- スケジュール頻度(1時間毎 / 1日1回)およびバッチサイズ(1回あたりの処理件数)は
  設定可能な値とし、初期値は `update_user.yml` 等の既存の日次スケジュールに揃える
  (1日1回)。頻度の最終決定は実装時にAPIレート制限の実測値を踏まえて調整する。
- 対象イベントの判定条件(どのフィールドが欠けていれば対象とするか)は、
  複数フィールドを同時に監視できる設計とし、1つのイベントが複数の欠落フィールドを
  持つ場合は1回の再取得でまとめて解消する。
