# Feature Specification: トーナメント単位でのイベント作り直し検知と空イベントの整理

**Feature Branch**: `005-tournament-event-sync`

**Created**: 2026-08-17

**Status**: Draft

**Input**: User description: "event_idからではなくtournamentからズレが発生していないかをチェックすればいいのではないでしょうか。例えばbackfillでそれを行うなど。置き換わったという判断は不要です。matches.jsonとstandings.jsonが空の場合消して、新しいevent_idの取得さえ行われば最終的なデータは整理された状態になるのでそれでよいです。"

## User Scenarios & Testing *(mandatory)*

`004-fix-duplicate-events` の実データ検証中に、第7回チバスマ交流会(tournament_id=811466)で
新しいパターンの不整合が見つかった。当初「開催日が延期され、同じイベント(event_id)が
別ディレクトリに保存された」と考えていたが、調査の結果、実際には**延期のタイミングで
start.gg側のイベント自体が作り直されていた**(event_id が `1423946` → `1533881` に変化)。

`004` で実装した重複解消・再取得ロジックはすべて event_id の一致を前提に動作するため、
この「同じ tournament_id の下で event_id そのものが変わる」ケースは構造的に検知できない。
さらに調査の結果、既存の自動取得経路(`update_tournament.yml` / `data_backfill.yml` /
`data_gap_check.yml` はいずれも `fetch_event_ids_from_tournament(tournament_id, game_id)`
経由)は、いずれも「今まさに有効なイベント一覧」を取得するだけで、過去に記録した
event_id との突き合わせ(差分検知)を一切行っていない。そのため、event_id が作り直されると、
新しい event_id は自動的には一切発見されず、古い event_id(既にstart.gg上には存在しない)
だけが空のデータを持ったまま残り続ける。

この状態を放置すると、同一 tournament_id に対して「実データが無い古い event_id のディレクトリ」
と「本来存在するはずだが未取得の新しい event_id」が非対称に残り続け、`004` が対象とする
重複(同一event_idが複数ディレクトリに存在するケース)とは別種のデータ不整合が
蓄積していく。

## Clarifications

### Session 2026-08-17

- Q: `tournaments.jsonl` 上の記録イベント数が0件になったトーナメント(User Story 2の削除により、唯一の記録イベントが無くなった場合)は、User Story 1の再チェック対象に含めるか？ → A: 含める。記録イベント数が0件であっても、`tournaments.jsonl` に記録済みのトーナメントである限り、新しいevent_idの発見(User Story 1)の対象とする。空イベント削除→新イベント未発見のまま取り残される事故を防ぐため。

### User Story 1 - トーナメント単位でイベントの作り直しを検知し、新しいイベントを取得する (Priority: P1)

データ利用者として、既に取得済みのトーナメントであっても、start.gg側でイベントが
作り直された(新しい event_id が追加された)場合には、それが既存の段階的な自動処理の
中で見つかり、通常のイベント取得と同じように保存されてほしい。

**Why this priority**: これが無いと、event_id の作り直しが起きるたびに人間が手動で
気づき、`event_id` を指定してツールを個別実行するしかなく、見逃されたイベントは
永久にデータセットに含まれない。

**Independent Test**: 既に1件のイベント(event_id)を記録済みのトーナメントに対して、
start.gg側の現在のイベント一覧に記録済みのものとは異なる event_id が含まれる状態を
用意し、トーナメント単位の定期チェックを1回実行して、新しい event_id のイベントが
新規に取得・保存されることを確認する。

**Acceptance Scenarios**:

1. **Given** 既に1件以上のイベントを記録済みのトーナメント、**When** start.gg側の現在の
   イベント一覧に、記録済みの event_id には無い新しい event_id が含まれている状態で
   トーナメント単位の定期チェックが実行される、**Then** その新しい event_id のイベントが
   通常の取得経路と同様に新規保存される。
2. **Given** start.gg側の現在のイベント一覧が記録済みの event_id と完全に一致している
   トーナメント、**When** 定期チェックが実行される、**Then** 何も新規取得されない
   (無駄なAPI呼び出し・書き込みが発生しない)。
3. **Given** User Story 2 の削除により記録済みイベント数が0件になったトーナメント、
   **When** トーナメント単位の定期チェックが実行される、**Then** そのトーナメントも
   再チェック対象に含まれ、start.gg側に新しい event_id があれば新規保存される。

---

### User Story 2 - 実データの無い空のイベントディレクトリを整理する (Priority: P2)

データ利用者として、`standings.json` と `matches.json` がどちらも空(参加者・試合結果が
0件)のイベントディレクトリが、既存の段階的な自動処理の中で自動的に削除され、
データセットに残り続けないようにしたい。

**Why this priority**: User Story 1 により新しい event_id が取得されるようになっても、
古い(作り直される前の、実データが無い)event_id のディレクトリは自動では消えず、
放置され続ける。両方が揃って初めて、最終的なデータセットが重複や空データの無い
整理された状態に収束する。

**Independent Test**: `standings.json` と `matches.json` がどちらも空のイベント
ディレクトリを用意し、整理処理を1回実行して、そのディレクトリが削除され、対応する
`tournaments.jsonl` の記録からも取り除かれることを確認する。

**Acceptance Scenarios**:

1. **Given** `standings.json` と `matches.json` がどちらも空(`data` 配列が0件)の
   イベントディレクトリ、**When** 整理処理が実行される、**Then** そのディレクトリは
   削除され、`tournaments.jsonl` の該当イベントの記録も削除される。
2. **Given** `standings.json` または `matches.json` のいずれかに1件以上のデータを
   持つイベントディレクトリ、**When** 整理処理が実行される、**Then** そのディレクトリは
   削除されない(実データは失われない)。

---

### Edge Cases

- 新しいイベントの発見(User Story 1)と、空イベントの削除(User Story 2)の間に、
  「削除対象の古いイベントが、実は新しく発見されたイベントと同一実体である」といった
  対応関係の判定は行わない(ユーザー確認済み: 判定不要。それぞれ独立に動作させれば、
  最終的に有効なデータだけが残る)。
- トーナメント自体が本当に中止され、start.gg側のイベント一覧が完全に空になった場合は
  どうなるか？ → 新規に発見されるイベントは無く、既存の空イベントディレクトリは
  User Story 2 の条件を満たせば削除される。トーナメント自体の記録(`tournaments.jsonl`
  の該当エントリ)を削除するかどうかは本機能のスコープ外とする(イベントが0件に
  なった場合の扱いは既存の `tournament_events_complete()` 等の挙動に委ねる)。
- 取得したばかりの新しいイベントがたまたま参加者0件だった場合はどうなるか？ →
  通常の取得結果としてそのまま保存される。次回以降のUser Story 2のサイクルで、
  空データのままであれば整理対象になり得る。
- `standings.json`/`matches.json` は空だが `seeds.json` には値がある場合はどうなるか？
  → `seeds.json` の中身は削除判定に含めない(ユーザー指定通り、判定基準は
  `standings.json` と `matches.json` の2ファイルのみ)。
- 大量のトーナメントを毎回全件チェックすると API 呼び出しが増大するため、既存の
  段階的バックフィル(`002-incremental-schema-backfill`)と同様、循環スキャン・
  1回あたりの処理件数制限の仕組みを踏襲する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、`tournaments.jsonl` に記録済みの各トーナメントについて(記録
  済みのイベント数が0件になっているトーナメントを含む)、start.gg側の現在のイベント
  一覧を再取得し、記録済みの event_id 集合に含まれない event_id を検出できなければ
  ならない。
- **FR-002**: システムは、FR-001で検出した新しい event_id について、既存の新規イベント
  取得と同じ手順(`attr.json`・`standings.json`・`seeds.json`・`matches.json` の取得)で
  保存しなければならない。
- **FR-003**: システムは、既存のイベントディレクトリのうち、`standings.json` と
  `matches.json` の両方が空(データ0件)であるものを検出できなければならない。
- **FR-004**: システムは、FR-003で検出した空のイベントディレクトリを削除し、対応する
  `tournaments.jsonl` の記録からも取り除かなければならない。
- **FR-005**: システムは、`standings.json` または `matches.json` のいずれかに1件以上の
  データを持つイベントディレクトリを、誤って削除してはならない。
- **FR-006**: 本機能の新規イベント発見(FR-001, FR-002)は、既存の `done.csv` ベースの
  完了判定(`004-fix-duplicate-events` で追加した開催日ベースの延期検知を含む)とは
  独立して動作し、一度「完了」と判定されたトーナメントに対しても新しいイベントの
  発見を妨げてはならない。
- **FR-007**: システムは、大量の一括再取得を避けるため、既存の段階的バックフィル
  機構と同様、循環的・カーソルベースでのスキャンを行い、1回の実行あたりに処理する
  トーナメント数を制限できなければならない。

### Key Entities *(include if feature involves data)*

- **トーナメントのイベント一覧差分**: ある tournament_id について、`tournaments.jsonl`
  に記録済みの event_id 集合と、start.gg側の現在の(ゲームでフィルタした)event_id
  一覧との差分。新規に追加されたものが本機能の取得対象。
- **空イベントディレクトリ**: `standings.json` と `matches.json` の両方が空の
  イベントディレクトリ。本機能の削除対象。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: start.gg側でイベントが作り直された(新しい event_id が追加された)
  トーナメントは、既存の段階的な自動処理の実行サイクルの中で(手動での event_id
  指定を行うことなく)新しいイベントが発見・取得される。
- **SC-002**: 参加者・試合結果がいずれも0件の既存イベントディレクトリは、既存の
  段階的な自動処理の実行サイクルの中で自動的に削除される。
- **SC-003**: 実データ(参加者または試合結果のいずれか)を持つイベントディレクトリが、
  本機能によって誤って削除されることはない。
- **SC-004**: 第7回チバスマ交流会(tournament_id=811466)について、本機能導入後の
  実行サイクルにより、event_id=1533881 が新規取得され、event_id=1423946 の空
  ディレクトリが削除される(=`004`で解消しきれなかったこのケースが最終的に
  整理された状態になる)。

## Assumptions

- 新しいイベントの発見と、空イベントの削除は、互いに独立した処理として実装する
  (どちらが「置き換え」なのかを判定するロジックは持たない、ユーザー確認済み)。
- 空判定の対象ファイルは `standings.json` と `matches.json` の2つに限定する
  (`seeds.json` や `attr.json` の中身は判定に使わない)。
- 空イベントディレクトリの削除は、現在ディスク上に保存されているファイルの中身
  (0件かどうか)のみで判断し、削除前に改めて start.gg へ再確認するかどうかは
  実装時の判断に委ねる(既存イベントは取得済み時点で `endAt` が過去である前提で
  保存されているため、改めての確認は必須要件としない)。
- 本機能は `data/startgg/tournaments.jsonl` に記録済みのトーナメントのみを対象とし、
  新規トーナメント自体の発見は既存の `download_all_tournaments()` に委ねる
  (本機能のスコープ外)。
- 実際の start.gg API アクセスを伴う一括処理(全トーナメントへの本機能の初回適用)は、
  既存の段階的バックフィルの通常サイクルに委ねる。第7回チバスマ交流会1件のみ、
  本機能の検証ケースとして実際の解消を確認する。
