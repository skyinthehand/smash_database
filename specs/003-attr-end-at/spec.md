# Feature Specification: イベント記録への大会終了日時(end_at)の保存

**Feature Branch**: `003-attr-end-at`

**Created**: 2026-08-07

**Status**: Draft

**Input**: User description: "end_at も attr.json に保存するようにして"

## User Scenarios & Testing *(mandatory)*

現在、各イベントの記録(`attr.json`)には大会の開始日時が `timestamp` として保存されているが、
終了日時は保存されていない。start.gg からは大会の終了日時(`endAt`)自体は既に取得できており、
実際に「まだ終了していない大会をスキップする」という判定にも使われているが、判定に使った後
その値は保存されずに捨てられている。

大会の終了日時を保存することで、開催期間(何日間開催されたか)や、大会終了から実際にどれだけの
時間が経ってからデータを取得できたか、といった分析が既存データへの再取得なしに行えるように
なる。

### User Story 1 - 新規・再取得イベントに終了日時を保存する (Priority: P1)

データ利用者として、新しく取得される、または再取得(バックフィル含む)されるイベントの記録に、
大会の開始日時だけでなく終了日時も含めてほしい。これにより、開催期間の分析や「大会終了から
何日後にデータが確定したか」といった集計を、start.gg に問い合わせ直すことなく行えるようにな
る。

**Why this priority**: これが実現しないと、終了日時を必要とする分析のたびに start.gg への
再アクセスが必要になり、`docs/data_model.md` に記載のイベント記録スキーマが不完全なままにな
る。

**Independent Test**: 大会情報(開始日時・終了日時を含む)を持つイベントを1件取得し、保存され
たイベント記録に終了日時が含まれていることを確認する。

**Acceptance Scenarios**:

1. **Given** start.gg 側で終了日時が確定している大会、**When** その大会のイベントが新規取得
   される、**Then** 保存されるイベント記録に開始日時と終了日時の両方が含まれる。
2. **Given** すでに終了日時なしで保存済みの既存イベント記録、**When** そのイベントが再取得
   (再ダウンロード)される、**Then** 保存されるイベント記録の終了日時が更新される。

---

### User Story 2 - 既存の全イベントにも段階的に行き渡らせる (Priority: P2)

メンテナとして、今回追加する終了日時のフィールドが、新規取得分だけでなく、既に保存済みの
全イベント記録にも、一度に全件再取得することなく、段階的に行き渡ってほしい。

**Why this priority**: この仕組みが無いと、終了日時を持つデータと持たないデータが恒久的に
混在し続け、[[既存の段階的バックフィル機構]]による解消が期待できなくなる。ただし、この
仕組み自体は既存の `event_data_version` ベースの段階的バックフィル(`002-incremental-schema-backfill`
で導入済み)を再利用することを前提とし、本機能では新しいバックフィル手段を新設しない。

**Independent Test**: 終了日時フィールドを持たない既存イベント記録に対してバックフィル処理を
1回実行し、対象イベントの記録に終了日時が追加されることを確認する。

**Acceptance Scenarios**:

1. **Given** 終了日時フィールドを持たない既存イベント記録、**When** 既存の段階的バックフィル
   処理がそのイベントを対象に実行される、**Then** イベント記録に終了日時が追加される。

---

### Edge Cases

- start.gg 側で大会の終了日時が未確定・未登録(nullを含む)の場合はどうなるか？ → 終了日時
  フィールドは「値なし」として保存され、取得処理自体は失敗させない。
- 個別イベント指定での取得(トーナメントslug指定など)のように、現状のクエリが大会の終了日時
  を取得していない取得経路がある場合はどうなるか？ → その経路でも終了日時を取得対象に含める
  必要がある(対象経路は実装時に洗い出す)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、新規に取得される全てのイベント記録に、大会の開始日時に加えて終了
  日時を保存しなければならない。
- **FR-002**: システムは、イベントの再取得(バックフィルによる再取得を含む)が行われた際、
  保存済みのイベント記録の終了日時を最新の値で更新しなければならない。
- **FR-003**: start.gg から取得した大会の終了日時が存在しない(未確定)場合、システムは取得
  処理自体を失敗させず、終了日時を「値なし」として記録しなければならない。
- **FR-004**: 終了日時は、既存の開始日時フィールドと同じ形式(同じ精度・タイムゾーン基準)で
  保存し、両者を直接比較できるようにしなければならない。
- **FR-005**: システムは、大会一覧からの一括取得、大会ID/イベントID指定での個別取得、既存
  イベントのバックフィルの、いずれの取得経路においても、終了日時を一貫して保存しなければ
  ならない。
- **FR-006**: 既存(本機能導入前)に保存されたイベント記録への終了日時の反映は、既存の段階的
  バックフィル機構を通じて行われ、そのために全件の一括再取得を必要としてはならない。

### Key Entities *(include if feature involves data)*

- **イベント記録**: 1つのイベント(大会内の1種目)についての属性情報。既に大会名・開催地・
  開始日時などを保持しており、本機能により大会の終了日時が新たに加わる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本機能導入後に新規取得されるイベント記録は、start.gg 側に終了日時が存在する
  限り、100%終了日時を含む。
- **SC-002**: 終了日時を持たない既存のイベント記録は、追加の手動一括再取得を行うことなく、
  既存の段階的バックフィルの通常の実行サイクルの中で終了日時を獲得できる。
- **SC-003**: データ利用者は、任意のイベント記録から、start.gg に再度問い合わせることなく、
  大会の開始日時と終了日時の両方を取得できる。

## Assumptions

- 「終了日時」は大会(トーナメント)全体の終了日時を指し、イベント(種目)ごとの個別の終了
  日時ではない。これは既存の「開始日時」フィールドが大会単位の値であることと整合させるため。
- 既存イベントへの反映は、新しいバックフィル専用の仕組みを新設せず、`002-incremental-schema-backfill`
  で導入済みの `event_data_version` ベースの段階的バックフィル機構(定期実行ワークフロー)を
  再利用する。
- 保存形式は既存の開始日時フィールドと同じ形式(UNIXタイムスタンプ相当)を踏襲する。
