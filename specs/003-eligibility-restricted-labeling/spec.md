# Feature Specification: 大会属性判定ロジックの内製化(参加資格制限大会ラベル)

**Feature Branch**: `003-eligibility-restricted-labeling`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "smash_databaseを利用している外部のイベントごとの判定もsmash_databaseの中に責務を移動させたいと考えています。具体的には、例えば参加資格制限大会かどうかという概念があり、トーナメント名もしくはイベント名に特定の文字列が含まれる場合は参加資格制限大会である、という判定を行っています。データ取得時にこれらの判定を行ってattr.jsonのlabelsにプロパティが追加されるほか、すでに存在するイベントデータすべてについて判定を適用してイベントデータを更新するツールも作りたいです。Startggのデータを新たに取り直すわけじゃないので、こちらはgithub actionsでの定期実行などは不要で単純な一連の処理として定義できるはずです。今の例の参加資格制限大会かどうか判定に使う文字列はどこかに定義してgitでバージョン管理できればOKです。"

## User Scenarios & Testing *(mandatory)*

現在、smash_database を利用する外部の消費者(アプリケーション等)は、独自に
「大会名またはイベント名に特定の文字列が含まれるかどうか」を見て、その大会が
「参加資格制限大会」(例: 特定の地域・所属・ランク等に参加資格を限定した大会)で
あるかどうかを判定している。この判定ロジックと、判定に使う文字列リストは
smash_database の外側に存在しており、smash_database 自身のデータ(`attr.json`)には
一切反映されていない。

この結果、判定ロジックや判定文字列を変更したい場合、smash_database 側からは
その変更履歴も現在の定義も追跡できず、複数の外部消費者がいる場合はロジックが
重複・乖離するリスクがある。

### User Story 1 - 新規取得イベントに参加資格制限ラベルを自動付与する (Priority: P1)

メンテナとして、start.gg から新規にイベントデータを取得する際に、
トーナメント名またはイベント名に登録済みの文字列が含まれていれば、
自動的に `attr.json` の `labels` に「参加資格制限大会である」ことを示す
プロパティを追加してほしい。これにより、外部消費者は自前で判定ロジックを
持たなくても、smash_database のデータを読むだけで判定結果を得られるようになる。

**Why this priority**: 外部への責務移動の入り口となる、最も基本的な価値。
これが無いと新規取得データにも判定結果が反映されず、外部消費者は
移行できない。

**Independent Test**: 判定文字列リストに含まれる文字列をトーナメント名に持つ
イベントを取得(または取得をシミュレート)し、`attr.json` の `labels` に
参加資格制限大会であることを示すプロパティが `true` で設定されることを確認する。
含まれないイベントでは `false`(または付与されない)ことを確認する。

**Acceptance Scenarios**:

1. **Given** トーナメント名に判定文字列リストのいずれかが含まれるイベントを取得する、
   **When** `attr.json` が書き出される、**Then** `labels` に参加資格制限大会である旨の
   プロパティが `true` で設定される。
2. **Given** イベント名(トーナメント名ではなく)に判定文字列が含まれるイベントを取得する、
   **When** `attr.json` が書き出される、**Then** 同様に `true` が設定される
   (トーナメント名・イベント名のどちらか一方でも一致すれば対象)。
3. **Given** トーナメント名・イベント名のどちらにも判定文字列が含まれないイベントを
   取得する、**When** `attr.json` が書き出される、**Then** 参加資格制限大会では
   ないことを示す値(`false`)が設定される。
4. **Given** `labels` に既存の他のプロパティ(例: OpenAI推定による `registration_type` 等)
   が存在するイベントを取得・更新する、**When** 参加資格制限大会の判定結果を書き込む、
   **Then** 既存の他のプロパティは保持されたまま、新しいプロパティのみが追加・更新される。

---

### User Story 2 - 既存の全イベントデータに判定を一括適用する (Priority: P1)

メンテナとして、既存の約26,000件超のイベントデータすべてに対して、
現在登録されている判定文字列リストを使って参加資格制限大会かどうかを判定し、
`attr.json` の `labels` を更新する一括処理ツールを実行したい。start.gg への
再アクセスは不要で、既に保存されている `tournament_name`/`event_name` の
文字列だけで判定できるため、スケジュール実行の仕組みは不要で、
必要なときに手動で1回(または文字列リスト変更のたびに)実行する
単純なツールでよい。

**Why this priority**: 新規取得分だけでなく、既存の大多数のイベントにも
判定結果が行き渡らなければ、外部消費者は smash_database だけを見て
判断できるようにならない。

**Independent Test**: 判定文字列リストに一致する/しないイベントを含む
一時イベントディレクトリ群を用意し、一括適用ツールを実行して、
該当する `attr.json` の `labels` だけが更新されることを確認する。

**Acceptance Scenarios**:

1. **Given** 判定文字列に一致するトーナメント名を持つ既存イベント、**When** 一括適用
   ツールを実行する、**Then** そのイベントの `attr.json` の `labels` に参加資格制限
   大会である旨のプロパティが追加・更新される。
2. **Given** 一括適用ツールを実行する、**When** start.gg への通信を監視する、
   **Then** 一切の外部APIリクエストが発生しない(既存のローカルデータのみで完結する)。
3. **Given** 判定文字列リストを変更した後に再度ツールを実行する、**When** 実行が
   完了する、**Then** 全イベントの判定結果が新しいリストに基づいて再計算され、
   古い判定結果が残らない(何度でも安全に再実行できる)。

---

### Edge Cases

- `tournament_name`/`event_name` が欠落・空文字列の場合 → 判定文字列に一致しないため
  「参加資格制限大会ではない」として扱う。
- 判定文字列リストが空の場合 → すべてのイベントが「参加資格制限大会ではない」と
  判定される(エラーにはしない)。
- `attr.json` 自体が存在しない、または JSON として壊れているイベントディレクトリ
  → 一括適用ツールはそのディレクトリをスキップし、処理を継続する(全体を
  停止させない)。
- 大文字小文字や全角半角の表記ゆれ → 単純な部分文字列一致(`in` 判定)とし、
  大文字小文字・全角半角の正規化は行わない。判定文字列リスト側で必要な表記
  バリエーションを網羅する運用とする(決定事項)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、参加資格制限大会かどうかを判定するための文字列のリストを、
  リポジトリ内の1箇所に定義し、git でバージョン管理しなければならない。
- **FR-002**: システムは、イベントの `tournament_name` または `event_name` のいずれかに、
  FR-001 のリストに含まれる文字列が部分一致で含まれる場合、そのイベントを
  「参加資格制限大会」と判定しなければならない。
- **FR-003**: システムは、start.gg から新規にイベントデータを取得する既存の経路
  (`scripts/fetch/download.py`, `scripts/fetch/download_specific_event.py`,
  `scripts/fix/redownload_event.py`, `scripts/fix/backfill_events.py`,
  `scripts/fetch/backfill_schema_version.py` など `attr.json` を書き出すすべての経路)
  において、FR-002 の判定結果を `attr.json` の `labels.registration_restricted`
  (真偽値: `true`/`false`)として書き込まなければならない。既存の `labels` に
  含まれる `registration_type` との命名一貫性を優先し、`registration_` を
  プレフィックスとするキー名を採用する。
- **FR-004**: FR-003 の書き込みは、`labels` に既に存在する他のプロパティ
  (例: OpenAI推定による `registration_type`/`event_type`/`game_rule`)を
  破壊してはならない(該当プロパティのみを追加・更新する)。
- **FR-005**: システムは、start.gg への再アクセスを行わず、既存イベントディレクトリに
  既に保存されている `tournament_name`/`event_name` の値だけを使って、既存の
  すべてのイベントデータに FR-002 の判定を適用し、`attr.json` の `labels` を
  更新するツールを提供しなければならない。
- **FR-006**: FR-005 のツールは、GitHub Actions 等によるスケジュール実行を必要とせず、
  必要なときに手動で実行できる単純なコマンドとして提供されなければならない。
- **FR-007**: FR-005 のツールは、`attr.json` が存在しない、または壊れている
  イベントディレクトリに遭遇しても処理全体を停止せず、そのディレクトリを
  スキップして残りの処理を継続しなければならない。
- **FR-008**: FR-005 のツールは、判定文字列リスト(FR-001)が変更された後に
  再実行しても安全であり(既存の判定結果を最新のリストに基づいて再計算する)、
  何度でも再実行可能でなければならない。

### Key Entities *(include if feature involves data)*

- **参加資格制限判定文字列リスト**: `tournament_name`/`event_name` に含まれていれば
  「参加資格制限大会」と判定するための文字列の集合。リポジトリ内のファイルとして
  git 管理される。
- **Event Directory**: `attr.json` を含む1イベント分のデータ一式
  (`001`/`002` と共通のエンティティ)。`tournament_name`/`event_name`/`labels` を
  参照・更新対象とする。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新規に取得されるイベントの100%について、`attr.json` の `labels` に
  参加資格制限大会かどうかの判定結果が、追加のAPI呼び出しなしに自動的に含まれる。
- **SC-002**: 既存の全イベントデータ(約26,000件超)に対して一括適用ツールを実行した
  結果、start.gg への外部APIリクエストが0件のまま、全イベントの `labels` に
  判定結果が反映される。
- **SC-003**: 判定文字列リストを変更してツールを再実行しても、`labels` 内の
  他の既存プロパティ(OpenAI推定分等)が変化しない。
- **SC-004**: 判定文字列リストの追加・変更が、コードの変更を伴わない
  (リストファイルの編集のみで完結する)形で行える。

## Assumptions

- 判定文字列リストの具体的な中身(実際にどの文字列が「参加資格制限大会」を
  示すか)は、本 spec の対象外とする。本機能が提供するのは「文字列リストを
  git管理し、それに基づいて判定・付与する仕組み」であり、初期のリストの内容
  (空でもよい)は実装時またはその後の運用の中で埋める。
- `labels` に追加するプロパティのキー名・値の型(真偽値か文字列か等)は、
  既存の外部消費者との将来的な互換性に関わるため、要クラリフィケーション
  (Edge Cases 参照)。
- 大文字小文字・全角半角等の正規化方針は、既存の外部ロジックの挙動に
  合わせることが望ましいが、本会話時点では不明なため要クラリフィケーション。
- 一括適用ツールは `scripts/fix/`(補完・検証・修復)配下に配置する想定
  (start.gg への再取得を伴わない、ローカルデータの修復・更新という性質のため)。
- 本機能で追加する判定は `002-incremental-schema-backfill` の
  `EVENT_DATA_VERSION`(start.gg から取得すべきデータの世代管理)とは無関係と
  扱う。ローカルの文字列照合のみで完結し、API再取得を伴わないため、
  スキーマバージョン管理・スケジュールバックフィルの対象外とする。
