# Feature Specification: 汎用イベントラベリング機構(大会名・イベント名ルールベース判定)

**Feature Branch**: `003-eligibility-restricted-labeling`

**Created**: 2026-08-01

**Revised**: 2026-08-30

**Status**: Draft

**Input**: User description(2026-08-30、再検討時): "制限大会判定の作業に戻る。もっと汎用的に作るべきということに気づいたため、
仕様から再検討したい。各大会のattr.jsonにlabelsプロパティをルールに基づいて追加することは変わらない。追加の仕様が以下。
ルールを更新することがありそうなため、label_versionプロパティを新設する。ラベルの付与はイベントデータ取得とは異なりstartgg
アクセスも不要でリポジトリ内のデータをプログラム判定するだけの高速処理なため別個に管理する。ただしラベルバージョンはイベント
データバージョンが特定以上である必要がある場合があるため、考慮できるようにする。次にルールはトーナメント名、イベント名ごとに
個別に判定できるようにする。つまりルール定義はjsonで以下の例のように指定したい(形式は同等のことができれば変更可): `{"version":
"1.0", "matches": [{"label": "registration_restricted", "tournament_name_match": "/制限/"}, {"label":
"registration_restricted", "event_name_match": "/制限/"}, {"label": "casual", "tournament_name_match": "/スマパ/",
"event_name_match": "/カジュアル/"}]}`"

(初版(2026-08-01)の入力は「参加資格制限大会かどうか」という単一の固定ラベルのみを
対象にしたものだったが、今回の再検討により、任意のラベルを宣言的なルールファイルで
定義できる汎用機構へと範囲を拡大する。「参加資格制限大会」はその汎用機構における
最初の(かつ引き続き重要な)ラベルの一例という位置づけになる。)

## User Scenarios & Testing *(mandatory)*

現在、smash_database を利用する外部の消費者(アプリケーション等)は、独自に
「大会名またはイベント名に特定の文字列が含まれるかどうか」を見て、その大会の
様々な属性(例: 参加資格制限大会かどうか、カジュアル大会かどうか等)を判定している。
この判定ロジックと判定に使うルールは smash_database の外側に存在しており、
smash_database 自身のデータ(`attr.json`)には一切反映されていない。

この結果、判定ロジックやルールを変更したい場合、smash_database 側からはその
変更履歴も現在の定義も追跡できず、複数の外部消費者がいる場合はロジックが
重複・乖離するリスクがある。また、対象とする属性(ラベル)が増えるたびに
専用の判定関数・専用のスキーマフィールドを追加する設計では拡張のたびに
コード変更が必要になってしまう。

### User Story 1 - 新規取得イベントにルールベースでラベルを自動付与する (Priority: P1)

メンテナとして、start.gg から新規にイベントデータを取得する際に、宣言的な
ルール定義ファイルに基づいて `tournament_name`/`event_name` を判定し、
該当する全てのラベルを自動的に `attr.json` の `labels` に追加してほしい。
これにより、外部消費者は自前で判定ロジックを持たなくても、smash_database の
データを読むだけで判定結果を得られるようになる。

**Why this priority**: 外部への責務移動の入り口となる、最も基本的な価値。
これが無いと新規取得データにも判定結果が反映されず、外部消費者は移行できない。

**Independent Test**: ルール定義ファイルに登録されたラベルのいずれかに一致する
トーナメント名・イベント名を持つイベントを取得(または取得をシミュレート)し、
`attr.json` の `labels` に該当ラベルが `true` で設定され、`label_version` に
適用したルール定義のバージョンが記録されることを確認する。一致しないイベントでは
該当ラベルが付与されない(またはキー自体が存在しない)ことを確認する。

**Acceptance Scenarios**:

1. **Given** ルール定義ファイルに、あるラベルの`tournament_name_match`条件を
   満たすトーナメント名を持つイベントを取得する、**When** `attr.json` が
   書き出される、**Then** `labels` に該当ラベルが `true` で設定され、
   `label_version` にそのルール定義のバージョンが記録される。
2. **Given** あるラベルの`event_name_match`条件を満たすイベント名(トーナメント名
   ではなく)を持つイベントを取得する、**When** `attr.json` が書き出される、
   **Then** 同様に該当ラベルが `true` で設定される。
3. **Given** あるラベルに`tournament_name_match`と`event_name_match`の両方が
   指定されている場合、**When** トーナメント名・イベント名のどちらか一方しか
   条件を満たさないイベントを取得する、**Then** そのラベルは付与されない
   (両方の条件を満たして初めて付与される)。
4. **Given** どのラベル条件にも一致しないイベントを取得する、**When**
   `attr.json` が書き出される、**Then** ルール管理対象のラベルは一切
   付与されない(`labels`にキー自体が存在しない)が、`label_version`は
   適用したルール定義のバージョンで記録される。
5. **Given** `labels` に既存の他のプロパティ(例: OpenAI推定による
   `registration_type` 等、ルール定義ファイルが管理しないキー)が存在する
   イベントを取得・更新する、**When** ルールベースの判定結果を書き込む、
   **Then** 既存の他のプロパティは保持されたまま、ルール定義ファイルが
   管理するラベルのみが追加・更新される。

### User Story 2 - 既存の全イベントデータに最新のルールを一括再適用する (Priority: P1)

メンテナとして、既存の約26,000件超のイベントデータすべてに対して、現在の
ルール定義ファイルを使ってラベルを再判定し、`attr.json` の `labels`/`label_version`
を更新する一括処理ツールを実行したい。start.gg への再アクセスは不要で、既に
保存されている `tournament_name`/`event_name` の文字列だけで判定できるため、
スケジュール実行の仕組みは不要で、必要なときに手動で1回(またはルール定義
ファイル変更のたびに)実行する単純なツールでよい。

**Why this priority**: 新規取得分だけでなく、既存の大多数のイベントにも
判定結果が行き渡らなければ、外部消費者は smash_database だけを見て
判断できるようにならない。

**Independent Test**: ルール定義ファイルに一致する/しないイベントを含む
一時イベントディレクトリ群を用意し、一括適用ツールを実行して、該当する
`attr.json` の `labels`/`label_version` だけが更新されることを確認する。

**Acceptance Scenarios**:

1. **Given** ルール定義ファイルのいずれかの条件に一致するイベント、**When**
   一括適用ツールを実行する、**Then** そのイベントの `attr.json` の
   `labels`/`label_version` が更新される。
2. **Given** 一括適用ツールを実行する、**When** start.gg への通信を監視する、
   **Then** 一切の外部APIリクエストが発生しない(既存のローカルデータのみで
   完結する)。
3. **Given** ルール定義ファイルを変更(ラベルの追加・条件の変更・
   `label_version`の更新)した後に再度ツールを実行する、**When** 実行が
   完了する、**Then** 全イベントの判定結果が新しいルールに基づいて
   再計算され、古い判定結果(新しいルールでは付与されなくなったラベル)が
   残らない(何度でも安全に再実行できる)。
4. **Given** あるイベントの`attr.json`の`label_version`が既に現在のルール
   定義の`label_version`と一致している、**When** 一括適用ツールを実行する、
   **Then** そのイベントは判定の再計算自体を行わずスキップされ、ファイルへの
   書き込みも発生しない(約26,000件超の規模での不要な再計算コストと
   diffノイズの両方を避ける)。

### User Story 3 - トーナメント名・イベント名を個別または組み合わせて判定するルールを定義できる (Priority: P2)

メンテナとして、1つのラベルに対して複数の判定ルールを登録でき、各ルールは
トーナメント名のみ・イベント名のみ・またはその両方の組み合わせ(両方とも
一致して初めて成立)のいずれでも判定できるようにしたい。同じラベルに対して
複数のルールを登録した場合は、そのいずれか1つでも成立すればラベルが付与される。

**Why this priority**: User Story 1・2 だけでも単一の固定ラベルなら実現できるが、
今回の再検討の主眼である「汎用化」(任意のラベルを、コード変更無しにルール
定義ファイルの追記だけで追加できるようにする)を実現する中核部分。これが
無いと、ラベルを増やすたびにコードの変更が必要になり、当初の目的
(判定ロジックを外部から smash_database に完全に移動する)を達成できない。

**Independent Test**: 「トーナメント名のみで判定するルール」「イベント名のみで
判定するルール」「両方の組み合わせで判定するルール」をそれぞれ含むルール
定義ファイルを用意し、それぞれの条件の組み合わせパターンに対して判定結果が
仕様通りになることを確認する。

**Acceptance Scenarios**:

1. **Given** `tournament_name_match`のみを指定したルール、**When**
   トーナメント名がそれに一致しイベント名は無関係なイベントを判定する、
   **Then** そのラベルが付与される。
2. **Given** `event_name_match`のみを指定したルール、**When** イベント名が
   それに一致しトーナメント名は無関係なイベントを判定する、**Then**
   そのラベルが付与される。
3. **Given** `tournament_name_match`と`event_name_match`の両方を指定した
   ルール、**When** 両方の条件を満たすイベントを判定する、**Then** そのラベルが
   付与される。
4. **Given** 同じラベルに対して複数のルールが登録されている、**When**
   そのうちの1つのルールにのみ一致するイベントを判定する、**Then**
   そのラベルが付与される(いずれか1つの成立で十分)。
5. **Given** 異なる2つのラベル(例: `registration_restricted`と`casual`)の
   条件をそれぞれ独立に満たすイベント、**When** そのイベントを判定する、
   **Then** `labels`にはその2つのラベルが両方とも`true`で同時に設定される
   (1イベントにつき1ラベルまでという制約は無い)。

### User Story 4 - ルールが新しいイベントデータ項目に依存する場合でも安全に運用できる (Priority: P3)

メンテナとして、将来的にラベル判定ルールが(トーナメント名・イベント名だけで
なく)より新しいイベントデータ項目を参照するようになった場合に備え、そのルール
定義が要求する最低限の `event_data_version` を宣言できるようにしたい。対象
イベントの `event_data_version` がその要件を満たさない場合、システムは
無理に判定せず、そのイベントの既存の `labels`/`label_version` を変更せずに
スキップしてほしい(必要なデータが揃っていないイベントに誤った判定結果を
残さないため)。

**Why this priority**: 現時点のルール(トーナメント名・イベント名の正規表現
一致)は既存のどの `event_data_version` のイベントでも判定可能であり、この
安全機構が無くても直ちに問題が起きるわけではない。しかし、ラベル付与の
仕組みとイベントデータ取得の仕組み(`002-incremental-schema-backfill`の
`EVENT_DATA_VERSION`)は別個に(別々のタイミングで)バージョン管理される
設計であるため、両者の間の依存関係を将来にわたって安全に扱える仕組みを
今のうちに用意しておく価値がある。

**Why this priority (優先度)**: 現在確定している要件ではなく将来への備えの
ため、P3(他の3つのUser Storyが完成した後で良い)とする。

**Independent Test**: 最低要求`event_data_version`を指定したルール定義
ファイルと、それを満たす/満たさないイベントデータを用意し、一括適用ツール・
新規取得経路の両方で、要件を満たさないイベントの`labels`/`label_version`が
一切変更されないことを確認する。

**Acceptance Scenarios**:

1. **Given** ルール定義ファイルに最低要求`event_data_version`が指定されて
   いる、**When** それを下回る`event_data_version`を持つ既存イベントに
   一括適用ツールを実行する、**Then** そのイベントの`labels`/`label_version`
   は変更されずスキップされる(かつスキップされた旨がツールの出力に
   記録される)。
2. **Given** 上記のスキップされたイベントについて、後日`event_data_version`
   が要件を満たす値まで更新される(`backfill_schema_version.py`等による)、
   **When** 一括適用ツールを再実行する、**Then** そのイベントも正常に
   判定され`labels`/`label_version`が更新される。
3. **Given** ルール定義ファイルに最低要求`event_data_version`が指定されて
   いない(または要求が無い)、**When** ツールを実行する、**Then** 全ての
   `event_data_version`のイベントが通常通り判定される(後方互換)。

---

### Edge Cases

- `tournament_name`/`event_name` が欠落・空文字列の場合 → どのルールにも
  一致しないため、当該ラベルは付与されない。
- ルール定義ファイルの`matches`が空(または存在しない)場合 → 全イベントに
  ついて、ルール管理対象のラベルは一切付与されない(エラーにはしない)。
- 正規表現として不正なパターンがルール定義ファイルに含まれている場合 →
  一括適用ツール・新規取得経路のどちらも、起動時にルール定義ファイル全体の
  妥当性を検証し、不正なパターンがあれば明確なエラーメッセージと共に処理を
  中止する(不正なルールのまま一部のイベントだけ判定される事態を避ける)。
- `attr.json` 自体が存在しない、または JSON として壊れているイベント
  ディレクトリ → 一括適用ツールはそのディレクトリをスキップし、処理を
  継続する(全体を停止させない)。
- 大文字小文字や全角半角の表記ゆれ → 正規表現の機能(必要なら文字クラス等)で
  ルール作成者側が表現する運用とし、システム側での自動正規化は行わない
  (決定事項、初版からの継続方針)。
- 過去に付与されたが現在のルールでは対象外になったラベル(ルール定義ファイル
  からラベル自体が削除された、または条件が変わり一致しなくなった場合) →
  一括適用ツールを再実行すると、ルール定義ファイルが現在管理する全ラベルの
  値が再計算されて置き換わるため、古い判定結果は残らない(User Story 2
  Acceptance Scenario 3参照)。ルール定義ファイルの管理対象外のラベル
  (OpenAI推定分等)には影響しない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、ラベル判定ルールをリポジトリ内の1箇所のファイルに
  宣言的に(JSON形式で)定義し、git でバージョン管理しなければならない。
  ルールファイルは、各ルールについて `label`(付与するラベル名)・
  `tournament_name_match`(トーナメント名に対する正規表現、省略可)・
  `event_name_match`(イベント名に対する正規表現、省略可)を指定できな
  ければならない。各ルールは `tournament_name_match`/`event_name_match`の
  少なくとも一方をMUST指定しなければならない。
- **FR-002**: あるルールに`tournament_name_match`のみが指定されている場合、
  システムはイベントの`tournament_name`がその正規表現に一致するかどうかのみで
  判定しなければならない(MUST、`event_name`は無視する)。`event_name_match`
  のみが指定されている場合も同様に`event_name`のみで判定する。両方が
  指定されている場合は、両方に一致した場合のみそのルールが成立する
  (MUST、AND条件)。
- **FR-003**: 同じ`label`に対して複数のルールが登録されている場合、
  システムはそのいずれか1つでも成立すれば、そのラベルをMUST付与しなければ
  ならない(OR条件)。異なる`label`同士の判定はMUST互いに独立して行われ
  なければならない: 1つのイベントが複数の異なるラベルの条件を同時に満たす
  場合、`labels`にはそれら全ての該当ラベルがMUST同時に設定されなければ
  ならない(1イベントにつき1ラベルまでという制約は無い)。
- **FR-004**: システムは、ルール定義ファイル全体に対して、そのルールセットを
  一意に識別する`label_version`(数値)をMUST定義できなければならない。
- **FR-005**: システムは、start.gg から新規にイベントデータを取得する既存の
  経路(`scripts/fetch/download.py`, `scripts/fetch/download_specific_event.py`,
  `scripts/fix/redownload_event.py`, `scripts/fix/backfill_events.py`,
  `scripts/fetch/backfill_schema_version.py` など `attr.json` を書き出す
  すべての経路)において、FR-001〜FR-003の判定結果を`attr.json`の`labels`に、
  適用したルール定義の`label_version`を`attr.json`の`label_version`
  (`event_data_version`と並ぶ独立したトップレベルフィールド)にMUST
  書き込まなければならない。
- **FR-006**: FR-005の書き込みは、`labels`に既に存在する、ルール定義ファイルが
  管理しないプロパティ(例: OpenAI推定による`registration_type`/`event_type`/
  `game_rule`)をMUST NOT破壊してはならない(該当プロパティのみを追加・更新
  する)。一方、ルール定義ファイルが管理するラベル(現在の`matches`に
  `label`として登場する全ての値)については、判定結果に基づいて毎回MUST
  完全に再計算しなければならない(過去に付与されたが現在は対象外になった
  ラベルを残さないため)。
- **FR-007**: システムは、start.gg への再アクセスを行わず、既存イベント
  ディレクトリに既に保存されている`tournament_name`/`event_name`の値だけを
  使って、既存の全てのイベントデータにFR-001〜FR-004の判定を適用し、
  `attr.json`の`labels`/`label_version`を更新するツールをMUST提供しなければ
  ならない。
- **FR-008**: FR-007のツールは、GitHub Actions等によるスケジュール実行を
  必要とせず、必要なときに手動で実行できる単純なコマンドとしてMUST提供
  されなければならない。
- **FR-009**: FR-007のツールは、`attr.json`が存在しない、または壊れている
  イベントディレクトリに遭遇しても処理全体をMUST NOT停止せず、そのディレクトリ
  をスキップして残りの処理を継続しなければならない。
- **FR-010**: FR-007のツールは、ルール定義ファイル(FR-001)が変更された後に
  再実行しても安全であり、何度でもMUST再実行可能でなければならない。対象
  イベントの`attr.json`の`label_version`が、現在のルール定義ファイルの
  `label_version`と既に一致している場合、システムはそのイベントについて
  判定の再計算自体をMUSTスキップしなければならない(判定処理を行わず、
  ファイルへの書き込みも発生しない)。一致していない(未設定・古い
  `label_version`を含む)イベントについてのみ判定を再計算し、結果が
  変化する場合のみファイルへMUST書き込まなければならない(不要な再計算
  コスト・差分の両方を避けるため)。
- **FR-011**: ルール定義ファイルは、そのルールセットの適用に必要な最低限の
  `event_data_version`を任意で宣言できなければならない(MAY)。宣言されて
  いる場合、システムは対象イベントの`event_data_version`がその値を下回る
  場合、FR-005・FR-007のいずれの経路でもそのイベントの`labels`/
  `label_version`をMUST NOT変更してはならず、スキップしなければならない
  (MUST)。
- **FR-012**: ルール定義ファイルに正規表現として不正なパターンが含まれている
  場合、システムはFR-005・FR-007のいずれの経路でも、判定処理を開始する前に
  MUSTこれを検出し、明確なエラーを報告した上で処理を中止しなければならない
  (一部のイベントだけが不正なルールで判定される事態を避ける)。

### Key Entities *(include if feature involves data)*

- **ラベルルール定義ファイル**(新規、`data/startgg/label_rules.json`
  を想定): `label_version`(数値)・`min_event_data_version`(数値、任意)・
  `matches`(ルールの配列)を持つ。各ルールは`label`(文字列)・
  `tournament_name_match`(正規表現文字列、任意)・`event_name_match`
  (正規表現文字列、任意)を持つ。リポジトリ内のファイルとしてgit管理される。
- **`attr.json.labels`**(既存、スキーマ拡張): 引き続きオブジェクト型。
  ルール定義ファイルが管理するラベルはキー名がラベル名・値が`true`の
  エントリとして(該当する場合のみ)追加される。ルール定義ファイルが
  管理しない既存のキー(OpenAI推定分等)は変更されない。
- **`attr.json.label_version`**(新規フィールド、`event_data_version`と
  並ぶ独立したトップレベルの数値): 現在の`labels`(のうちルール管理対象分)を
  算出したルール定義ファイルの`label_version`を記録する。本機能導入前の
  既存イベント、および`min_event_data_version`要件を満たさずスキップされた
  イベントには存在しない(またはそれ以前の値のまま)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新規に取得されるイベントの100%について、`attr.json`の
  `labels`/`label_version`に、追加のAPI呼び出しなしにルール定義ファイルに
  基づく判定結果が自動的に含まれる。
- **SC-002**: 既存の全イベントデータに対して一括適用ツールを実行した結果、
  start.gg への外部APIリクエストが0件のまま、`min_event_data_version`要件を
  満たす全イベントの`labels`/`label_version`に判定結果が反映される。
- **SC-003**: ルール定義ファイルを変更してツールを再実行しても、
  ルール定義ファイルが管理しない`labels`内の既存プロパティ(OpenAI推定分等)が
  変化しない。
- **SC-004**: 新しいラベルの追加・既存ラベルの条件変更が、コードの変更を

- **SC-005**: 同一ラベルに対し、トーナメント名のみ・イベント名のみ・両方の
  組み合わせのいずれの条件でもルールを表現でき、複数ルールのいずれか1つの
  成立でラベルが付与されることを、実データ相当のテストケースで100%確認できる。

## Assumptions

- ラベルの具体的な種類・判定に使う正規表現パターンの内容は、本spec の対象外
  とする。本機能が提供するのは「ルール定義ファイルをgit管理し、それに基づいて
  判定・付与する汎用機構」であり、初期のルール内容(空でもよい)は実装時
  またはその後の運用の中で埋める。「参加資格制限大会」(`registration_restricted`)
  は、この汎用機構を使って表現される最初のラベルの一例として引き続き重要だが、
  唯一のラベルではない。
- `tournament_name_match`/`event_name_match`の正規表現は、Pythonの`re`モジュール
  相当の構文とし、大文字小文字・全角半角の正規化は行わない(ルール作成者側が
  正規表現の機能で表現する)。入力例にある`/パターン/`という前後スラッシュ
  記法は、他言語の正規表現リテラル記法に倣った可読性のための任意の記法であり、
  実装時にスラッシュの有無どちらも受け付けるかは`/speckit-plan`で確定する。
- ルール定義ファイルの`label_version`は、ルールの内容を変更するたびに
  メンテナが手動で増分する整数とする(`EVENT_DATA_VERSION`と同様の運用)。
  自動採番の仕組みは持たない。
- `min_event_data_version`は、ルールセット全体に対して1つだけ宣言できる
  (個別のルールごとには宣言しない)。現時点のルール(トーナメント名・
  イベント名の正規表現一致)はどの`event_data_version`でも判定可能なため、
  実際に運用でこの値が1より大きくなるのは、将来トーナメント名・イベント名
  以外のフィールドを参照するルールが追加された場合のみと想定する。
- 一括適用ツールは`scripts/fix/`(補完・検証・修復)配下に配置する想定
  (start.gg への再取得を伴わない、ローカルデータの修復・更新という性質の
  ため)。
- `label_version`は`002-incremental-schema-backfill`の`EVENT_DATA_VERSION`と
  完全に独立した、別個のバージョンカウンタとして扱う(FR-011の依存関係
  チェックを除き、両者は互いに関与しない)。
- 初版(2026-08-01)で示されていた「`labels`の値は真偽値」という前提は
  維持するが、キーの集合が固定(`registration_restricted`のみ)ではなく
  ルール定義ファイルの`matches`に登場する`label`値によって可変になる点が、
  今回の再検討による最大の変更点である。
