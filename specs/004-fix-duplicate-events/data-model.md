# Data Model: 大会延期による重複イベントディレクトリとattr.json欠落の解消

本機能は新しいデータフィールド・新しいファイルを追加しない。既存の2つのエンティティに対する
「決定ロジック」「発見ロジック」「更新タイミング」の振る舞いを変更する。

## エンティティ

### イベントディレクトリ (`data/startgg/events/{Region}/{YYYY}/{MM}/{DD}/{Tournament}/{Event}/`)

- 既存フィールド・既存ファイル構成(`attr.json` / `standings.json` / `seeds.json` /
  `matches.json`)は変更しない。
- **振る舞いの変更**: 同一 `event_id` に対して、過去に記録されたパスと異なる新しいパスで
  データが完全に書き込まれた場合、古いパスのディレクトリは削除される(同一 `event_id` の
  ディレクトリは常に高々1つ)。
- **振る舞いの変更**: `attr.json` を欠いたディレクトリ(`standings.json` 等の他ファイルは
  存在する)も、段階的バックフィルの発見対象に含まれるようになる。

### `tournaments.jsonl` のイベント記録 (`events[]` 配列の各要素)

既存フィールド(`event_id`, `event_name`, `path`)は変更しない。

- **振る舞いの変更**: 既に `event_id` が記録済みのエントリであっても、実際の保存先パスが
  変わった場合は `path` フィールドが新しいパスで上書きされる(従来は追加のみで更新されな
  かった)。

## 状態遷移: イベントの保存先パス

```
[未取得]
   │ 新規取得
   ▼
[パスA に保存済み] ──(delayなし)──▶ 変化なし(定常状態)
   │
   │ start.gg 側で開催日が変更された状態で再取得される
   ▼
[パスA が存在, パスB への書き込み中]
   │
   ├─ パスB の必須ファイルが揃わないまま処理終了(大規模イベント失敗等)
   │     ▼
   │  [パスA(旧, 完全) + パスB(新, 不完全) が併存] ── 次回実行で再度統合を試みる
   │
   └─ パスB の必須ファイルが揃う
         ▼
      [パスA 削除, tournaments.jsonl の path が B に更新される]
         ▼
      [パスB に保存済み](定常状態、パスAは存在しない)
```

## 発見ロジックの入出力(`backfill_schema_version.iter_event_dirs`)

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 走査キー | `attr.json` の存在 | `attr.json` または `standings.json` の存在(和集合) |
| 発見されるディレクトリ | `attr.json` を持つイベントディレクトリのみ | `attr.json` の有無に関わらず、取得が試みられた全イベントディレクトリ |
| 戻り値の型 | `list[Path]`(ディレクトリ) | 変更なし |
| ソート順(Japan優先) | 維持 | 維持(`002-incremental-schema-backfill` / 既存の Japan 優先ロジックに変更なし) |

## `backfill_one_event()` の event_id 解決フロー

```
1. event_dir/attr.json を読む
   ├─ 成功し event_id が取れる → その event_id を使う(従来通り)
   └─ 失敗 or event_id が無い
        ▼
2. tournaments.jsonl を読み、events[].path == str(event_dir) となるエントリを探す
   ├─ 見つかる → そのエントリの event_id を使い、再取得を続行
   └─ 見つからない
        ▼
3. [UNRESOLVED] としてログ出力・レポートに記録し、この1件をスキップ(処理全体は継続)
```
