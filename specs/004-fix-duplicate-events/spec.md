# Feature Specification: 大会延期による重複イベントディレクトリとattr.json欠落の解消

**Feature Branch**: `004-fix-duplicate-events`

**Created**: 2026-08-14

**Status**: Draft

**Input**: User description: "第7回チバスマ交流会が2つ存在します。またattr.jsonがないものも存在します。どういう状態か調べてバグを洗い出し、修正方針を考えて修正して"

## User Scenarios & Testing *(mandatory)*

`data/startgg/events/Japan/2025/08/16/第7回チバスマ交流会/` と
`data/startgg/events/Japan/2026/02/07/第7回チバスマ交流会/` に、同一の大会(tournament_id=811466,
event_id=1423946)が2つのディレクトリとして重複して存在している。調査の結果、原因は以下の通り。

1. イベントの保存先ディレクトリは取得時点の大会開始日時(startAt)から決め打ちで計算される。
   start.gg 側で開催日が延期(2025-08-16 → 2026-02-07)されると、新しい日付のディレクトリが
   別物として新規作成され、古い(延期前の、entrant数0件の空データが入った)ディレクトリは
   削除・統合されずそのまま残る。
2. 大会が再取得されても、`tournaments.jsonl` に記録されたイベントの保存先パスは常に古いまま
   更新されない(既知の event_id を持つイベントはパスの更新処理自体が実行されないバグ)。
   これにより、以後の完了判定(`should_skip_tournament`)は実体と食い違う古いパス上のファイル
   存在だけを見て「完了済み」と誤判定し続け、新しい方のディレクトリの不完全さが検知されない。
3. 大規模イベントの取得(セット情報のページネーション)が失敗すると、`attr.json` を書き込む
   処理に到達する前に処理が打ち切られる。新しいディレクトリ(2026/02/07)はまさにこの状態で、
   `standings.json`・`seeds.json`・`matches.json` はあるが `attr.json` が存在しない。
4. 既存の段階的バックフィル(`002-incremental-schema-backfill`)は `attr.json` の存在を起点に
   対象イベントを発見する仕組みのため、`attr.json` が欠落しているイベントは発見の対象にすら
   ならず、通常運用では永久に補完されない。

同様のパターンは第7回チバスマ交流会に限らない。`data/startgg/events` 全体で、`attr.json` が
存在しないイベントディレクトリが661件、また日付違いで同一名の大会ディレクトリが複数存在する
ケースが他にも複数件確認されている(例: 走利夜-SO-RYA_#2、L.S.C.T〜Love_Smash_Champion_Tournament〜、
晴れスマ#47/#43、下克上#97/#119 など)。

## Clarifications

### Session 2026-08-14

- Q: 既に3件以上重複している大会(例: 走利夜-SO-RYA_#2、L.S.C.T〜Love_Smash_Champion_Tournament〜)について、本機能はどこまで自動的に解消するか？ → A: 軽量版のみ実装する(`tournaments.jsonl` に記録された1件の旧パスとの比較のみで統合)。第7回チバスマ交流会のような2ディレクトリの重複と、今後発生する新規の延期は自動解消の対象とするが、既に3件以上重複しているケースで `tournaments.jsonl` からも参照されていない「中間の」ディレクトリの自動検出・削除は本機能のスコープ外とし、`docs/fix.md` に既知の制約として記録する。

### User Story 1 - 大会延期による重複ディレクトリを作らない・解消する (Priority: P1)

データ利用者として、同じ大会・同じイベントが、開催日の延期によって別々のディレクトリの記録
として重複して存在してほしくない。ある大会が延期され再取得されたときは、新しい開催日の
ディレクトリに一本化され、古い(延期前の)ディレクトリは残らないでほしい。

**Why this priority**: 重複が解消されない限り、集計・分析のたびに同一大会を二重にカウントする
リスクが残り、データセットの信頼性そのものが損なわれる。

**Independent Test**: 既に保存済みのイベント(event_id)に対応する大会の開始日時が変わった状態
で再取得を実行し、実行後に該当 event_id のディレクトリが新しい開催日のパス1つだけになって
いること、`tournaments.jsonl` の記録パスも新しいパスに更新されていることを確認する。

**Acceptance Scenarios**:

1. **Given** 過去に取得済みのイベント(event_id)を含む大会、**When** start.gg 側でその大会の
   開催日時が変更された状態で再取得が行われる、**Then** そのイベントの記録は新しい開催日の
   ディレクトリに保存され、古い開催日のディレクトリは残らない。
2. **Given** 既に重複して存在している第7回チバスマ交流会の2ディレクトリ、**When** 本機能の
   修正を適用して該当イベントを再処理する、**Then** 最終的に1つの(2026/02/07の)ディレクトリ
   に一本化され、2025/08/16側のディレクトリは残らない。

---

### User Story 2 - attr.jsonが欠落したイベントを段階的バックフィルで確実に補完する (Priority: P2)

データ利用者として、大規模イベント等で取得処理が途中で打ち切られ `attr.json` を含む一部の
ファイルが欠落した場合でも、それが放置されず、既存の段階的バックフィルの通常の実行サイクルの
中で最終的に補完されてほしい。

**Why this priority**: 発見の仕組み自体が `attr.json` の存在を前提にしている限り、欠落した
イベントは何度バックフィルを回しても永久に見つからず修復されない。全661件がこの状態で
放置され続けることになる。

**Independent Test**: `attr.json` を持たない(が `standings.json` 等の他のファイルは持つ)
イベントディレクトリを用意し、既存の段階的バックフィル処理を1回実行して、そのイベントが
再取得対象として検出され、実行後に `attr.json` が新規作成されることを確認する。

**Acceptance Scenarios**:

1. **Given** `standings.json`・`seeds.json`・`matches.json` の一部または全部はあるが
   `attr.json` を持たないイベントディレクトリ、**When** 段階的バックフィル処理が実行される、
   **Then** そのディレクトリが再取得対象として検出され、`attr.json` が新規に作成される。
2. **Given** `attr.json` すら存在しないためイベントIDが直接読み取れないディレクトリ、
   **When** バックフィル処理がそのディレクトリを検出する、**Then** ディレクトリ構造・
   既存ファイル(`tournaments.jsonl` 等)から可能な範囲でイベントIDを特定し再取得を試みるか、
   特定不能な場合はエラーとせず人が確認できる形で報告する。

---

### User Story 3 - 再取得後もブックキーピングが実体と食い違わないようにする (Priority: P3)

メンテナとして、イベントの保存先ディレクトリが再取得によって変わった場合、`tournaments.jsonl`
のような完了判定に使う記録が実体を反映するよう更新され、以後の完了判定が古い情報に基づいて
誤ってスキップし続けないようにしたい。

**Why this priority**: これが直らないと、User Story 1・2 を個別に直しても、将来また同種の
延期や取得失敗が起きるたびに同じ現象(重複・欠落の見逃し)が再発する。根本原因の除去に当たる。

**Independent Test**: 既知の event_id を持つイベントを、保存先ディレクトリが変わる状態で
再取得し、`tournaments.jsonl` 内の該当イベントの記録パスが新しいディレクトリを指すよう更新
されていることを確認する。

**Acceptance Scenarios**:

1. **Given** `tournaments.jsonl` に古いパスで記録済みの event_id を含む大会、**When** その
   大会が(開催日変更などにより)新しいパスで再取得される、**Then** `tournaments.jsonl` の
   当該イベントの記録パスが新しいパスに更新される。

---

### Edge Cases

- 延期後の再取得が完了する前に処理が再度中断した場合(重複解消の途中で再度大規模イベント
  失敗が起きた場合)はどうなるか？ → 古いディレクトリはまだ削除せず、新しいディレクトリが
  完全に完成した(必須ファイルが揃った)ことを確認できてから初めて古いディレクトリを削除・
  統合する。中途半端な状態で古いデータを失うことがあってはならない。
- 同じ大会が2度以上延期され、3つ以上の日付ディレクトリが存在する場合はどうなるか？ →
  `tournaments.jsonl` に記録されている1件の旧パスとの統合のみ自動的に行われる(最新の
  ディレクトリと、記録されている旧パスの2つが1つに統合される)。`tournaments.jsonl` から
  も参照されていない、それ以外の(中間の)重複ディレクトリの自動検出・削除は本機能の
  スコープ外とし、既知の制約として `docs/fix.md` に記録する(Clarifications 参照)。
- 延期ではなく、たまたま同名で全くの別大会・別イベント(別の tournament_id / event_id)が
  複数日にわたって存在する場合はどうなるか？ → event_id が異なる場合は重複とみなさず、
  それぞれ独立したイベントとして扱う(本機能の対象はあくまで同一 event_id の重複)。
- `attr.json` が欠落しており、かつ `tournaments.jsonl` 側にもそのイベントの記録が一切ない
  (どちらからも event_id を特定できない)場合はどうなるか？ → 自動修復の対象外とし、人手で
  確認が必要なケースとして一覧化・報告する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、既に保存済みの event_id を持つイベントを再取得する際、大会の開催
  日時が変わっていた場合、新しい開催日のディレクトリにデータを保存した上で、
  `tournaments.jsonl` に記録されている(そのイベントの)古い開催日のディレクトリを残さない
  (削除または統合する)ようにしなければならない。`tournaments.jsonl` から参照されていない
  それ以外の重複ディレクトリの自動解消は対象外(Assumptions 参照)。
- **FR-002**: システムは、イベントの再取得後、そのイベントの必須ファイル(`attr.json` を
  含む)一式が新しいディレクトリに揃うまでは、古いディレクトリを削除してはならない(削除は
  新ディレクトリの完成を確認できてから行う)。
- **FR-003**: システムは、イベントを再取得しディレクトリのパスが変わった場合、`tournaments.jsonl`
  等の完了判定に使うブックキーピングの記録パスを新しいパスに更新しなければならない。
- **FR-004**: システムの完了判定(スキップ判定)は、ブックキーピングに記録された情報だけで
  なく、実際に走査対象となるディレクトリの内容とも整合していることを前提としてはならない
  — ブックキーピングが古い場合でも、実体が不完全なイベントは再取得対象として検出できなければ
  ならない。
- **FR-005**: 既存の段階的バックフィルの対象発見ロジックは、`attr.json` の存在有無に依存せず、
  必須ファイル(`attr.json`・`matches.json`・`standings.json`・`seeds.json`)の一部が欠落
  しているイベントディレクトリも検出しなければならない。
- **FR-006**: `attr.json` が欠落しているために event_id を直接読み取れないイベントディレク
  トリに対しては、`tournaments.jsonl` などの既存の記録から event_id を特定できる場合はそれを
  用いて再取得を試み、特定できない場合はエラーで処理全体を止めることなく、人が確認できる形で
  一覧として報告しなければならない。
- **FR-007**: 本機能の修正は、第7回チバスマ交流会(tournament_id=811466, event_id=1423946)
  の重複を実際に解消できることをもって検証しなければならない。
- **FR-008**: システムは、同一 event_id を持たない(たまたま大会名・イベント名が同じだけの)
  ディレクトリ同士を、誤って重複とみなして統合してはならない。
- **FR-009**: `tournaments.jsonl` からも参照されておらず、本機能の自動解消の対象外となる
  既知の重複ディレクトリ(3件以上の重複が既に存在するケースの中間ディレクトリ等)について、
  システム(または本機能導入時のPR)は、その制約の内容を `docs/fix.md` に記録しなければ
  ならない。

### Key Entities *(include if feature involves data)*

- **イベントディレクトリ**: `data/startgg/events/{地域}/{年}/{月}/{日}/{大会名}/{イベント名}/`
  以下に保存される、1イベント分の記録一式(`attr.json`・`standings.json`・`seeds.json`・
  `matches.json`)。保存先パスは取得時点の大会開始日時から計算される。
- **tournaments.jsonl のイベント記録**: 大会(tournament_id)ごとに、その大会に含まれる各
  イベント(event_id)の保存先パスを記録するブックキーピング。完了判定(スキップ判定)に
  使われる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 第7回チバスマ交流会は、修正適用後、`data/startgg/events` 内に重複なく1つの
  ディレクトリとしてのみ存在する。
- **SC-002**: 大会の開催日が延期された場合でも、以後の再取得によって重複ディレクトリが新たに
  発生することはない(`tournaments.jsonl` に記録された最新の旧パスとの統合が毎回行われる
  ため、延期のたびにディレクトリが増え続けることはない)。
- **SC-003**: `attr.json` が欠落しているイベントは、既存の段階的バックフィルの通常の実行
  サイクルの中で(追加の一括手動再取得を行うことなく)発見され、補完される。
- **SC-004**: イベントの保存先パスが再取得によって変わった場合、`tournaments.jsonl` の記録
  パスは実体と一致した状態を保つ。

## Assumptions

- 重複解消の判断基準は event_id の一致とする。event_id が同じであれば同一イベントとみなし、
  最新の(現在の start.gg 上の開催日に基づく)ディレクトリを正とする。
- 古いディレクトリの削除は、対応する新しいディレクトリの必須ファイル一式が揃っていることを
  確認できた場合にのみ行う(データを失うより、重複が残る方が安全という既存の方針を踏襲する)。
- `attr.json` 欠落661件全件の実データ再取得(start.gg への実アクセスが必要)は、本セッションの
  サンドボックス環境に実アクセス手段がないため、本機能では発見・検出ロジックの修正までを
  スコープとし、実際の再取得の実行は既存の段階的バックフィルの通常サイクル(または人手による
  `workflow_dispatch` 実行)に委ねる。これは `003-attr-end-at` の T018 と同様の制約。
- `tournaments.jsonl` の更新や重複解消は、既存の `chore-update` ブランチ運用・自動コミットの
  仕組みを変更せず、その枠組みの中で動作するロジックとして実装する。
- 重複ディレクトリの自動解消は `tournaments.jsonl` に記録されている1件の旧パスとの統合のみを
  対象とする(軽量版)。events_root 全体を event_id 基準で走査し、3件以上残っている既存の
  重複ケース(走利夜-SO-RYA_#2、L.S.C.T〜Love_Smash_Champion_Tournament〜等)の
  「どこからも参照されていない中間ディレクトリ」まで一括検出・削除する仕組みは、実装・検証の
  コストが大きいため本機能のスコープ外とし、`docs/fix.md` に既知の制約として記録した上で
  別途の機能として扱う(Clarifications 参照)。
